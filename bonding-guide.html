Step-by-step guide · OpenMPTCProuter v0.64.x

Self-hosted link bonding without a cloud provider

Bond 5 Starlink dishes and 1 cellular modem on a mini PC running OpenMPTCProuter (OMR), tunnelled to your own always-on far-end box on a separate internet line with a real public IP. The far end merges every path and hands you one public address.

See the animated diagram

⚠ Read this first: the far-end line is the speed ceiling

Total bonded speed can never exceed the far-end line's own upload and download. Every byte you download is first received by the far-end box and then sent back up its line to you, so your bonded download is capped by the far-end upload; your bonded upload is capped by the far-end download.

If the public-IP line sits at the same shop, the bonded traffic goes out over the dishes and comes straight back in on that same line. Bonding then mainly adds failover (one stable public IP that survives a dish dropping), not extra speed. For real speed gains, put the far-end box somewhere else, on a line with more upload than all your WANs combined.

2Install & configure OMR on the mini PC

2.1 Flash the image

  1. Download the x86_64 factory image for v0.64.x from openmptcprouter.com (sysupgrade images are only for upgrades).
  2. Write it to the mini PC's SSD / NVMe or a USB key with balenaEtcher, or on Linux:
gunzip openmptcprouter-*.img.gz
dd bs=4M if=openmptcprouter-*.img of=/dev/sdX conv=fsync
  1. Boot the mini PC, plug a laptop into the LAN port, and open http://192.168.100.1/. Login root with an empty password — set a password immediately (System → Administration).

2.2 Prepare each WAN device

  • Put each Starlink router in bypass mode (or use the Starlink Ethernet adapter) so OMR gets the address directly; otherwise give each Starlink router a different LAN subnet.
  • For a modem/router: disable its DHCP or give it a unique subnet (e.g. 192.168.11.1) and disable IPv6 on it so traffic can't leak past OMR. USB dongles appear as a ModemManager / QMI interface.
  • If you use a VLAN switch: create VLANs 11–16 (one per WAN) as untagged access ports to the dishes, all tagged on the trunk port to the mini PC.

2.3 Run the wizard

  1. Go to System → OpenMPTCProuter → Wizard.
  2. Server IP: your far-end public address, e.g. 203.0.113.10. Server key: the key printed at the end of the server script (e.g. EXAMPLE-KEY-0000-REPLACE-ME). Changing the key makes the wizard fetch settings from the server.
  3. Add one interface per WAN: wan1…wan5 = Starlink (DHCP, on the right port or VLAN device such as eth0.11), wan6 = cellular (DHCP or ModemManager). For static modems set IP/gateway/netmask, e.g. IP 192.168.11.2, gateway 192.168.11.1, 255.255.255.0.
  4. On every WAN set Multipath TCP = enabled. Optional: set the cellular link to backup if it has a data cap — it is then only used when all dishes fail.
  5. Leave the default VPN (MQVPN in 0.64) and default proxy unless you have a reason to change. Save & apply.
  6. Open Status: every WAN should show green with its public IP, and the server should show as reachable with an API answer.
In 0.64 you can also set per-interface weights (Network → Interfaces, or the MPTCP page) to favour the stronger dishes. Leave defaults first, tune later.

3Far-end server setup (your own box, not a VPS)

3.1 Install the official OMR server script — bare metal preferred

  1. Clean install of Debian 12 (x86_64), wired, with a static LAN address (e.g. 192.168.1.50) and correct clock (NTP on).
  2. As root, run the official script (it installs the OMR MPTCP kernel, VPNs, proxies, firewall):
wget -O - https://www.openmptcprouter.com/server/debian-x86_64.sh | sh
  1. At the end the script prints the server key and other credentials; they are also saved in /root/openmptcprouter_config.txt. Copy the key into the router wizard. Never paste it into public docs or chats.
  2. SSH moves to port 65222. Reboot so the new kernel loads, then reconnect with ssh -p 65222 root@192.168.1.50.
  3. To update later, re-run the same command (0.64.2 needs server ≥ 0.1081).
Docker / LXC: containers share the host kernel. They only work if the host kernel already has MPTCP enabled (upstream 5.6+, net.mptcp.enabled=1) and the container is allowed to manage networking; the script cannot install its kernel inside a container. Bare metal or a full KVM VM avoids all of this.

3.2 Port forwarding on the public-IP router

Forward from the far-end router's WAN (203.0.113.10) to the server's LAN IP (192.168.1.50). Simplest: forward TCP + UDP 65000–65535 (the range the official docs suggest). Main ports per the wiki:

PortUse
65500 TCPOMR JSON admin API (wizard / server key)
65001 TCP+UDPGlorytun
65101 / 65280 TCP+UDPShadowsocks / Shadowsocks-Rust
65301 TCPOpenVPN
65311–65312 UDPWireGuard
65228–65231, 65248–65252 TCPV2Ray / XRay (443 if VLESS-Reality)
65400 TCP+UDPiperf3
65222 TCPSSH (optional; better reach it over the tunnel or VPN only)

MQVPN (the 0.64 default VPN) uses a configurable port in the OMR range, or 443 in "port 443 mode" — forward whatever you set. Disable SIP ALG / "smart" filtering on that router. Since the server takes over traffic for the public IP, any services the shop exposes get forwarded through OMR's port-forwarding page, which pushes rules to the server.

4MPTCP kernel requirements

  • Upstream Linux has MPTCP since 5.6; OMR 0.64 uses modern 6.x kernels (6.12 / 6.18) on both sides. The server script installs a matching kernel — keep it as the default GRUB entry.
  • Check MPTCP is on:
uname -r
sysctl net.mptcp.enabled          # must be 1
sysctl -w net.mptcp.enabled=1     # enable if 0
ip mptcp limits show              # subflows / add_addr_accepted
ip mptcp endpoint show            # one endpoint per WAN (router side)
  • OMR configures endpoints and limits for you. With 6 WANs the limits must allow ≥ 6 subflows, e.g. ip mptcp limits set subflows 8 add_addr_accepted 8 — normally only needed when debugging by hand.
  • On the router, the MPTCP → Diagnose tab explains fallback, blackhole and reset problems in plain English.

5Routing — what OMR does for you

  • Each LAN TCP connection is carried by the proxy/VPN as one MPTCP connection with one subflow per WAN; OMR creates the per-WAN routing tables and source rules automatically.
  • Return traffic (your downloads) is spread by the server side across those same subflows — the far end acts as the merge point and the internet only ever sees 203.0.113.10.
  • UDP and non-TCP traffic goes through the multipath VPN (MQVPN by default).
  • mwan3 / policy routing / load-balancer not needed — don't add them, they fight OMR's own routing. OMR-Tracker handles link health and failover.
  • Use OMR-ByPass only for things that must skip the tunnel (e.g. a site that needs a Starlink IP).

6Testing

  1. Baseline before bonding: run a speedtest on each dish and the modem alone, and on the far-end line (note its upload!).
  2. Through the tunnel from the OMR shell (SSH to the router): 
    omr-test-speed            # aggregated download (run ≥ 2 min, Ctrl+C)
omr-test-speed eth1       # one WAN only
omr-iperf                 # aggregated, server → router
omr-iperf vps -R          # reverse direction
# or plain iperf3 against the server's iperf port:
iperf3 -c 203.0.113.10 -p 65400 -P 8 -t 30 -R
  3. Status page: watch per-link bandwidth on each WAN during the test — all six should carry traffic. The Metrics page shows health score per link.
  4. Speedtest after: from a LAN PC; the shown IP must be 203.0.113.10 (your far-end public IP).
  5. Pull-a-cable test: start a long download / video call, unplug one dish, then the modem. The session should continue; OMR-Tracker marks the link down within seconds. Plug back and confirm it rejoins.

7Failure points & fixes

ProblemFix
Starlink CGNATFine — OMR only makes outbound connections to the server. Only the far end needs a public IP.
Dish obstruction / outagesCheck the Starlink app's obstruction map, remount higher; OMR fails over, but a flapping dish lowers throughput — set it to backup until fixed.
Speed stuck at a low ceilingFar-end line upload is the hard cap (see warning box). Also check the far-end router's CPU for NAT throughput.
Some sites hang, small pings OKMTU / MSS: lower WAN MTU (e.g. 1400–1450 on cellular) and let OMR manage the tunnel MTU; don't force a static MTU on the MQVPN device.
"Can ping server, no API answer"Port 65500 not forwarded, ISP blocks the high ports, or fail2ban on an older server — update server to ≥ 0.1081 and check forwarding. Test with nc -vz 203.0.113.10 65500 from outside.
ISP blocks ports / UDPSwitch the VPN to TCP-based (OpenVPN/Glorytun TCP) or MQVPN port 443 mode; ask the ISP to lift filtering.
Traffic flows but no aggregationKernel lacking MPTCP: sysctl net.mptcp.enabled must be 1 on the server; reboot into the OMR kernel; containers need host support.
Tunnel/keys rejected, TLS errorsClock/time wrong — enable NTP on both ends (System → System → time sync on OMR; timedatectl set-ntp true on Debian).
Names don't resolve / DNS hijack warningsLet OMR handle DNS (it sends queries through the tunnel); set LAN clients to use the router; check the DNS hijacking alert.
Far-end IP changesYou need a static public IP, or use a DNS name in the wizard and a DDNS client at the far end.
